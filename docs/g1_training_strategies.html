§2 根因 · Root cause

HumanoidBench 把 H1 和 G1 放到了两个完全不同的控制问题上。 不是网络宽度、不是 obs 维度、不是 act 维度——而是 actuator 类型本身。
HumanoidBench puts H1 and G1 into two fundamentally different control problems — not net width, obs dim, or act dim, but the actuator type itself.
H1（成功）G1（失败）
Actuator XML<position kp="200" kv="5"/><motor ctrlrange="-88 88"/>
控制语义Policy 输出目标关节角度，PD 控制器自动 servoPolicy 输出裸扭矩，无任何 inner loop 帮助
Action 物理范围例如 hip ∈ [-0.43, 0.43] radhip ∈ [-88, 88] N·m
每步动作连续性关节角速度受 PD 限制，自然平滑无内置平滑，policy 自己学
稳定性PD 提供自动减速 + 抗扰完全依赖 policy 学到的"会站着"
exploration_noise=0.2 的语义每步 ±0.086 rad 微扰每步 ±17.6 N·m 巨扰，机器人会被推飞
HumanoidBench __init__.py:6if robot == "g1" or robot == "digit": control = "torque" — 硬编码强制 G1 用 torque
关键数学事实：DR.Q 在归一化 [-1, 1] action 空间施加 N(0, 0.2) 高斯噪声。在 H1 pos 上这是 4% 关节范围，policy 收敛过程中扰动可忽略；在 G1 torque 上这是 ±17.6 N·m 即 ±20% 满力矩，策略每一步都被持续推动，根本无法稳定。这就是为什么 G1-crawl ckpt mean 比 random 还低 — 训练时加噪声让 policy 偏向"狂躁"策略。

§6 失败回退路径 · Fallback if PD doesn't work

如果 §4 跑出来 G1 pos 仍达不到 H1 量级（success < 50%），按此顺序回退：

  1. 降 exploration_noise 0.2 → 0.1 → 0.05（Tier A 方案 A'）
  2. 加 action smoothness L2 penalty（Tier B 方案 G）
  3. 切 PPO 训练（Tier A 方案 D-i）
  4. 训 1M 步而非 500k（Tier B 方案 F）

不做：加宽网络 / H1 warm-start / DR / curriculum — 这些都不解决根因。

§8 OpenCode 的颠覆性诊断 · OpenCode's reframing

OpenCode 指出 Opus + Codex 都错了真正根因。
G1 现在跑的 g1_torque.xml 已经被 patch 成 PD position 控制（见 §4.2），但训练仍慢得多。问题不在 PD vs torque，而在 G1 action 空间维度组成。

8.1 真正根因（更精准）

分组DoF 数与行走关系
腿 + 躯干13必需
手臂10有用（平衡/摆臂）
手指14完全无关
合计37

DR.Q (DRQ.py:133) 对所有 37 维施加同方差噪声 σ=0.2：

action += torch.randn_like(action) * 0.2  # 37-dim isotropic Gaussian
致命数学：所有 37 维噪声落在 [-σ, σ] 内的联合概率 = 0.68³⁷ ≈ 10⁻⁷。
意思是：每一条 transition 都至少有一个关节被大幅扰动。其中 14 维是与行走无关的手指。

H1 (19D, 全部 walk-relevant): 0.68¹⁹ ≈ 7×10⁻⁴ — 还可以容忍
G1 (37D, 14D 是手指): 每个 transition 都被手指噪声污染

8.2 污染链 / Contamination chain

  1. 每个 transition 混入手指随机痉挛 → encoder 的 dynamics loss (dyn_weight=1.0) 被迫学习"无关手指动力学"
  2. InfoNCE 对比学习被混淆：两条 transition 行走相同但手指动作不同 → encoder 学不到行走相关的不变表征
  3. LAP 优先重放的 priority 被 finger-heavy 的 dynamics error 劫持
  4. 250k 步灾难性遗忘：encoder 从"行走动力学"漂移到"手指动力学" → Value 函数崩塌 → 策略崩塌

"G1-crawl random 378 vs 训练后 350" 完美证实：random policy 关节不动 = 稳定爬；训练后 policy 输出 + 噪声搅动手指 = 比 random 更差。

10.2 关键发现总结

  1. OpenCode 诊断完全正确：14 维手指 noise 污染 encoder 是真根因之一。BH 在 50k-100k 早期已 1.5× 快于 PD-only，最终 500k 步爆发到 700+
  2. "中后期 BH 比 PD-only 慢"是误判：第二次接力 290k 数据看起来 BH 落后，但 BH 末段急速上升（440k mean 354 → 470k peak 476 → 500k mean 711）。教训：不要在 60% 进度时根据 deterministic 3-ep eval 下结论
  3. PD（Opus/Codex）+ BlockedHands（OpenCode）是组合最优：单独 PD 把 mean 从 100→435（4.3×）；BlockedHands 在 PD 基础上从 435→711（再 1.6×）；总增益 7.1×
  4. eval.py 修了 BlockedHandsLocoWrapper 导致 success_bar 检测失败的 bug：原 env.task.success_bar 因 wrapper cycle 不可达；fallback 按 env_id 字符串匹配的 task name 查表
所有三模型贡献都得到验证：
Opus 找到 PD vs torque 接口差异 → 解决 80%
Codex 引用业界证据（HF G1 PPO ckpt 都用 PD targets）→ 强化 PD 方向
OpenCode 挖出 14 维手指 noise 污染 → 解决剩余 20%
